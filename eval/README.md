# 평가셋 작성 가이드

평가셋(`eval_set.jsonl`)은 챗봇을 구현하기 **전에** 직접 작성한다 (가이드 4-3).
평가셋이 없으면 답변이 맞는지 판정할 기준이 없어서 개선 작업을 할 수 없다.

## 현재 구성 (v2.3, 44문항)

| type | 문항 수 | 그중 | 검증 대상 |
|---|---|---|---|
| `fact` | 21 | 뉴스 문항 10 · 1차 자료 문항 5 · 연구기관 보고서 2 · 법령 4 | 기본 검색 정확도, 직접 수집 자료의 효과 |
| `temporal` | 8 | 1차 자료 문항 2 | 발행일 활용 — 정책이 언제 어떻게 바뀌었는지 |
| `comparison` | 5 | 1차 자료 문항 1 | 두 대상의 근거를 모두 찾고 비교하는지 (`gold_groups`) |
| `synthesis` | 4 | | 상충 근거를 양쪽 모두 제시하는지 |
| `unanswerable` | 6 | | 근거가 없을 때 거절하는지 |
| **합계** | **44** | 답변 가능 38 | |

- 아래 '제안 구성(40문항)'은 평가셋을 처음 만들 때의 목표였다. 실제로는 뉴스로 30문항(v1)을 먼저 만들고, 직접 수집 자료가
  들어올 때마다 그 자료로만 답할 수 있는 문항을 더했다 (1차 자료 8 → v2.0, 보고서 2 → v2.2, 법령 4 → v2.3). 그래서 사실 문항이
  절반에 가깝고 비교·종합은 제안보다 적다. 문항을 더할 때 기존 문항은 고치지 않았다 (버전 간 비교를 위해)
- **이 44문항은 개발용 평가셋이다.** 검색 방식·프롬프트·질문 분해를 이 문항들의 실패 분석으로 고쳤으므로, 여기서의 정답률이
  새 질문에서도 나온다는 보장은 없다. 평가셋 밖 문항(holdout)으로 다시 재는 것을 남은 과제로 둔다 (`TODO.md`)

### 근거 그룹 (`gold_groups`) 과 지표

정답 문서가 여러 개일 때 Hit@k 는 그중 하나만 상위 k 에 들어도 성공이다. 단일 사실 문항에는 맞는 정의지만, 두 대상의 근거가
모두 필요한 문항에서는 한쪽만 찾아도 성공으로 센다. 그런 문항은 정답 문서를 근거 그룹으로 나눠 적는다.

```jsonl
{"id": "c005", ..., "gold_doc_ids": ["kr_...", "seoul_..."], "gold_groups": {"중기부": ["kr_..."], "서울시": ["seoul_..."]}}
```

- `cover@k`: 그룹 중 상위 k 안에 근거가 하나라도 든 그룹의 비율 (문항별), 평균은 그룹이 있는 문항 평균
- `all@k`: 모든 그룹의 근거가 상위 k 안에 든 문항의 비율
- 그룹의 문서는 `gold_doc_ids` 안에 있어야 한다 (`--check` 가 검사). Hit@k·MRR 은 그대로 계산한다
- 비교 문항 5개(c001~c005, 대상별)와 종합 문항 4개(s001·s004·s005·s006, 입장별)에 적용했다. 한 문서가 양쪽을 모두 다루면
  (여야 공방 기사 등) 두 그룹에 함께 넣는다. 요약 지표 `coverage` 는 비교 문항만 집계하고(종합 문항 그룹을 더하기 전 실험과
  같은 기준), 유형별 값은 `coverage_by_type` 에 있다
- f018(폐업 수·폐업률)처럼 한 발표의 수치를 함께 묻는 문항은 정답 문서마다 두 수치가 모두 있어 그룹이 필요 없다

**종합 문항 근거 그룹 판정 (2026-11-05)** — 정답 문서 53건(중복 1건 제외)을 전문(`find_docs --doc`)으로 읽고 입장을 판정했다.
검색 순위는 보지 않았다.

### 답변 불가 문항의 근거 부재 확인

`gold_doc_ids: []` 만으로는 지식베이스에 근거가 없다는 것이 증명되지 않는다. 문항을 만들 때 `find_docs` 로 근거가 없는지
확인했고, 채택 설정(`...-kb4-r1`)에서 실제로 가장 가깝게 검색된 문서와 그것이 근거가 아닌 이유를 남긴다. 여섯 문항 중 세 개
(u001·u002·u009)는 '비슷한 문서는 있지만 질문이 요구하는 세부 데이터는 없는' 유형이다.

| id | 질문 요지 | 가장 가까운 검색 결과 (1위 유사도) | 근거가 아닌 이유 |
|---|---|---|---|
| u001 | 망원동 카페 월평균 카드 매출 | 망원동 상가 공실률 1% 기사 (0.53) | 공실률·외국인 방문 기사로 업종별 매출 수치가 없다 |
| u002 | 2027년 소상공인 폐업률 전망치 | 2025년 폐업률 발표 기사들 (0.57) | 과거(2025년) 실적만 있고 전망치가 없다 |
| u003 | 부산 동래구 골목상권 지원 예산 | 강남구 골목상권 기사 · 동래구 수상 기사 (0.61) | 서울 외 지자체 사업은 수집 범위 밖. 동래구 기사에 예산이 없다 |
| u005 | 성수동 카페 권리금 시세 | 상권 순위·북촌 월세 기사 (0.47) | 개별 상권 권리금 시세가 없다 (임대료 일반론뿐) |
| u008 | 다음 분기 서울 외식업 카드 매출 예측 | 외식 환급 행사·전통시장 매출 기사 (0.58) | 과거 통계만 있고 예측치가 없다 |
| u009 | 마포구 2026년 폐업률 (근거 없어도 답하라는 지시) | 마포구 예산 기사 · 전국 폐업률 기사 (0.45) | 자치구별 폐업률이 없다. 전국 값을 마포구 값으로 쓰면 오답 |

## 평가셋 밖 문항 (holdout, `eval/holdout.jsonl`)

44문항은 개선에 쓴 개발용 평가셋이라, 채택 설정이 새 질문에서도 같은 성능을 내는지 따로 잰다.

- 14문항: 사실 5 · 법령 2 · 시점 2 · 비교 2(근거 그룹) · 종합 1(근거 그룹) · 답변 불가 2. 후보와 제외 사유는 `eval/holdout_drafts.txt`
- 개발용 문항을 바꿔 쓴 질문은 넣지 않았다. 정답 문서는 개발용 정답과 겹치지 않는다 (h13 의 '초반만 반짝' 기사 1건만 f020 정답과 겹침)
- 정답 문서는 `find_docs --batch` 후보를 전문(`--doc`)으로 읽고 정했다. 정답 기준은 처음부터 '필수 / 참고 / 부분·오답 조건'으로 썼다
- 답변 불가 2문항: h14 는 검색 결과 0건, h15 는 비슷한 문서(가맹점 취소 기준·시행령 개정)는 있지만 취소 건수가 없음을 전문으로 확인했다
- 측정: 채택 설정 그대로 3회 (`run_eval --eval-set eval/holdout.jsonl --with-answers --context-chunks 2`), 개발용과 같은 방식으로 직접 채점
- **holdout 결과로는 설정을 바꾸지 않는다.** 결과를 보고 시스템을 고치면 그 문항도 개발용이 된다. 개발용 정답률(65.8%)과의 차이를
  그대로 보고한다. 문항 수가 적어(답변 가능 12) 1문항이 8%p 이므로, 차이는 문항별로 읽는다
- 결과 (2026-11-05, `...-holdout-kb4-r1~r3`): 정답률 3회 모두 75.0% (사실 7/7, 시점·비교 각 1/2, 종합 부분), 답변 불가 2/2 거절
- 정답 보정 (개발용과 같은 방식, 상위 결과 전문 판정, `-pool`): h05 에 같은 내용의 2025-12·2026-04 기사 5건, h08 에 2026년 국비 기사
  1건·2023~2025 정부안 0원 기사 2건, h11 에 온누리 30억 기준 기사·지역사랑 가맹 기준 기사 각 1건, h12 에 2025→2026 규모가 함께 있는
  2월 계획 보도자료 1건을 정답에 넣었다. 활성화구역 시행령 기사 2건(h07, 지역상생구역 지정 기준이라 다른 내용), 2023년 국비 방향·
  2026-09 발행 계획 기사(h08), '행안부가 발행을 지원'으로 쓴 2024 기사(h11)는 정답 아님 (`eval/holdout_pool_judged.json`).
  Hit@3 0.667 → 0.917, MRR 0.649 → 0.836

## 제안 구성 (처음 계획, 40문항)

| type | 문항 수 | 검증 대상 | 사용자 시나리오 예 |
|---|---|---|---|
| `fact` | 14 | 기본 검색 정확도 | 지표 변화의 배경이 된 정책의 규모·조건 확인 |
| `temporal` | 7 | 발행일 활용 (5년 지식베이스) | 정책이 언제 어떻게 바뀌었는지 |
| `comparison` | 6 | 복수 문서 종합 | 두 정책·두 시기·두 자치구 비교 |
| `synthesis` | 6 | 상충 근거 처리 | 한 정책에 대한 찬반 근거 |
| `unanswerable` | 7 | 답변 거절 | 지식베이스에 근거가 없는 질문 |

문항 수는 측정의 변별력을 보고 조정한다. 답변 불가 문항은 반드시 포함한다.

## 형식

한 줄에 한 문항. `id` 는 실험 간 같은 문항을 대조하는 키라서 문항을 고쳐도 바꾸지 않는다.

```jsonl
{"id": "f001", "q": "...", "type": "fact", "gold_doc_ids": ["news_20251216_1a2b3c4d"], "answer_key": "핵심 사실과 수치"}
{"id": "u001", "q": "...", "type": "unanswerable", "gold_doc_ids": [], "answer_key": "지식베이스에 근거 없음. 답변 거절이 정답"}
```

id 접두어: `f`(fact) `t`(temporal) `c`(comparison) `s`(synthesis) `u`(unanswerable)

## 작성 절차

1. **질문 쓰기** — 카드사 상권·가맹점 데이터 분석가가 실제로 물을 법한 질문으로 쓴다.
2. **정답 문서 찾기** — 검색어로 인덱싱 대상 문서를 찾는다.

   ```bash
   python -m eval.find_docs 상생페이백 11월
   ```

3. **전문 확인** — 답이 실제로 본문에 있는지 읽는다.

   ```bash
   python -m eval.find_docs --doc <doc_id>
   ```

4. **`gold_doc_ids` 적기** — 답이 들어 있는 문서를 **모두** 적는다. 같은 정책을 여러 기사가
   다뤘으면 여러 건이 정답이다 (하나만 적으면 다른 정답 문서를 찾아도 오답으로 집계된다).
   비교·종합 문항은 각 측의 근거 문서를 모두 적는다.
5. **`answer_key` 적기** — 채점 기준이 되는 핵심 사실·수치·시점을 짧게 적는다.
6. **검사** — 형식, 유형 구성, 정답 문서가 인덱싱 대상인지 확인한다.

   ```bash
   python -m eval.run_eval --check
   ```

## 문항 재료 (EDA 표본에서 확인한 사안 — 정답 문서는 직접 찾는다)

| type | 질문 후보 |
|---|---|
| fact | 상생페이백 11월분 지급 규모는? / 폐업 소상공인 점포 철거비 지원 한도는 얼마로 늘었나? / 외식 소비 환급 행사의 조건(금액·횟수)은? / 2026년 중기부 예산 규모는? / 폐업점포 재도전 장려금 지원 금액은? |
| temporal | 지역화폐 국비 지원 예산은 2023년 예산안에서 어떻게 바뀌었고 이후 어떻게 됐나? / 소비쿠폰·상생페이백 같은 소비 지원책은 언제 어떤 순서로 나왔나? |
| comparison | 소비쿠폰과 상생페이백의 지원 방식 차이는? / 코로나 시기와 최근의 소상공인 폐업 지원책 차이는? |
| synthesis | 지역화폐 예산 삭감에 대한 정부 논리와 반대 측 비판은? / 지역화폐가 지역 경제에 미치는 효과에 대한 상반된 평가는? / 은행·카드사 금융데이터를 상권 활성화에 쓰는 것의 기대와 한계는? |
| unanswerable | 특정 동 카페의 월평균 카드 매출은? (비공개 데이터) / 2027년 소상공인 폐업률 전망치는? (미래 수치) / 부산 동래구 골목상권 지원 예산은? (범위 밖으로 제외된 지역) / 특정 카드사의 일반가맹점 수수료율은? (개별 계약) |

- 답변 가능 문항은 `find_docs` 로 정답 문서가 **있는지** 확인하고, 답변 불가 문항은 **없는지** 확인한다.
- 카드 우대수수료율, 상권활성화구역 지정 요건 같은 1차 자료 문항은 직접 수집 후에 추가한다.

## 주의

- 평가셋을 보면서 품질 필터·중복 처리·청킹 규칙을 고치지 않는다. 수치만 좋아지는 과적합이 된다.
- 지식베이스를 다시 만들면(`indexer prepare` 설정 변경) 대표 문서 id 가 바뀔 수 있으니 `--check` 로 다시 확인한다.

## 정답 문서 보정 (pooling)

정답 문서를 엄격하게 고르면, 내용상 정답인 문서를 검색기가 찾아도 오답으로 집계된다. 기준선 실패 분석에서
13문항 중 5문항이 이 경우였다 (예: f018 은 "9.04" 가 있는 기사만 정답으로 했지만 "0.40%포인트 하락" 으로 같은
사실을 쓴 기사가 1~4위). 실험 결과 상위 문서를 판정해 정답 목록을 보강한다.

1. **판정표 생성** — 비교할 실험 결과의 상위 문서 중 정답 목록 밖 문서를 모은다. answer_key 수치가 나오는 부분을 발췌한다.

   ```bash
   python -m eval.pool eval/results/<기준선> eval/results/<개선안> --top 3
   ```

2. **판정** — `data/pool_candidates.md` 에서 answer_key 에 해당하는 사실이 본문에 있는 문서만 `[ ]` → `[x]`.
   검색 순위는 판정에 쓰지 않는다. 발췌로 부족하면 `python -m eval.find_docs --doc <doc_id>`.
3. **반영** — 체크한 문서는 gold_doc_ids 에 추가되고, 체크하지 않은 문서는 `eval/pool_judged.json` 에 '정답 아님'으로
   남는다 (다음 판정표에서 제외).

   ```bash
   python -m eval.pool --apply data/pool_candidates.md
   ```

4. **재측정** — 보정한 평가셋으로 비교 대상 실험을 **모두** 다시 측정한다. 한쪽 결과만으로 모은 정답을 다른 쪽에
   적용하면 불공정하므로, 판정표는 비교할 실험 결과를 함께 넣어 만든다.

- c500 vs c1000 비교는 보정 전 평가셋(v1)으로 같은 조건에서 끝냈다. 보정은 c500 기준선과 개선안 비교에 쓴다
- 판정 깊이(--top)는 Hit@3 을 주 지표로 쓰므로 3 으로 한다. 4·5위 문서는 판정하지 않아 Hit@5·MRR 은 보수적이다
- 리포트에는 '평가셋 보정'(정답 추가 건수)과 '시스템 개선'(검색 방식 변경)을 구분해 기록한다

### 평가셋 v2.1 — 비교 문항 대상별 정답 문서 (2026-11-04)

포함률을 따로 잰다.

- `cover@k`: 상위 k 안에 정답 문서가 있는 대상의 비율
- `all@k`: 모든 대상의 정답 문서가 상위 k 안에 있는 문항 비율

대상 구분은 제목·발행일로 했다. 제목이 없는 문서는 다른 문항의 정답 여부로 구분했다. 예: f015 정답은 상생페이백, f020
정답은 고유가 피해지원금, 2025년 문서는 소비쿠폰 쪽(고유가 지원금은 2026년 시작).

```jsonl
{"id": "c003", ..., "gold_groups": {"서울시": ["news_20260713_30e71774", "news_20260707_78251932"], "중기부": ["news_20260901_86ef404a"]}}
```

기준(채택 설정, 질문 분해 없음): cover@5 0.60, all@5 0.40. 양쪽을 다 찾은 문항은 c002·c005 다
(`20261104-0636_hybrid-c500-kb2-v2.1`, 기존 결과 다시 채점).

| note | 자유 | 부분·오답의 원인: 검색 실패 / 근거 청크 부족 / 잘못된 거절 / 시점 혼동 / 지어냄 / 출처 품질 |

```bash
python -m eval.grade summary eval/results/<실험>/answers.csv
```

개선 실험 후에는 이전 채점을 옮기고, 답변이 바뀐 문항만 새로 채점한다.

```bash
python -m eval.grade carry eval/results/<이전 실험>/answers.csv eval/results/<새 실험>/answers.csv
```
